Multi-Agent Systems, Agent Memory and Tool Use

Three more boxes of the agent skeleton. Several agents can debate or be coordinated by an orchestrator; memory (episodic, semantic, procedural) carries state across long tasks that no context window can hold; and tools, from Toolformer's five APIs to Gorilla's 1,600, let the model hand off work it can't do reliably itself.

1 · Multi-agent debate ▶ 40:49

Besides self-consistency and reflection, another way researchers improved reasoning was multi-agent debate: several agents solve the same task; after each round, each reads the others' reasoning and they debate, like discussing a decision with teammates; drawing on the diverse perspectives, they reach a final decision.

The assumption back then was that each individual model wasn't strong enough, so debate was a way to prompt more out of it. ▶ 41:34 With today's powerful models, if your only goal is a performance boost, multi-agent setups won't help much. Other design considerations can still favour them:

  • Efficiency.
  • Data access control: one agent handles health care, another handles sensitive information, each seeing only its own data.

2 · Orchestration ▶ 42:03

Another pattern: many specialised agents plus an orchestrator that coordinates them toward one task. In Microsoft's early Magentic-One, the orchestrator breaks a big task into parts and assigns each to a specialist (the first part to a file-surfing agent, then a coder, then a computer terminal, and so on); at the end it combines the results into a final answer for the user.

Multi-agent debateOrchestrator + specialists
Who does whatEveryone solves the same taskEach agent gets a different sub-task
How they combineRead each other's reasoning, argue, convergeOrchestrator merges the pieces
Why use itDiverse perspectives when single models were weakDecomposition, specialisation, access control

3 · Why agents need memory ▶ 43:03

Memory is a place for lots of creative design. Two reasons it's needed:

  1. Capacity. Context windows keep growing, but still can't hold the whole event stream. An agent working on your project for three-plus hours generates a lot of data.
  2. Relevance. Even if it fit, finding the relevant piece is hard: with 1,000 documents in context, locating the right one each time is slow because the search space is huge.

Generative agents (Smallville) ▶ 44:25 simulate people living in a small town. Their design needs a memory stream to keep track of what happened to each individual so the story can continue.

5 · Tool use: Toolformer ▶ 46:30

Agents now use many kinds of tools (search, coding, …); tool use gets its own lecture next Wednesday. In early work, the tool call was triggered inside decoding. Take "The New England Journal of Medicine is a registered trademark of …": at that point the model emits a special QA call, "Who is the publisher of The New England Journal of Medicine?", gets the answer, and uses it in the rest of the generation. So teaching tool use meant learning where to call an API, when, and which one.

Toolformer ▶ 48:05 was roughly the first work to teach LLMs tools this way, with just five: a calculator, a question-answering system, a search engine, a translation system and a calendar. A very limited set, but today's tool-using agents are inspired by setups like this.

6 · Tool use: Gorilla ▶ 48:46

Gorilla (Berkeley) teaches LLMs to use thousands of APIs. It collected over 1,600 APIs from Hugging Face, Torch Hub and TensorFlow Hub, generated synthetic training data from them, and trained a 7-billion-parameter model.

At inference, a user says "I want to see some cats dancing in celebration"; Gorilla retrieves the right API (likely a Stable Diffusion model) and an image comes out. Without the tool, the base model itself would need image-generation ability; with it, the work is delegated. The results: very few hallucinations and high accuracy, which makes sense, since otherwise the model must do everything from its own parameters, whereas with tools its generation can be more factual and reasonable.

7 · The whole skeleton ▶ 50:31

LLM core that reasons and plans · memory carrying state across steps and tasks · tools reaching out to many APIs · an environment to act in and observe. Every agent you build, whether it writes code, browses the web or runs a terminal, is a version of this diagram. What differs is how each box is implemented and how well the pieces fit together.

8 · Q&A: how does an agent know what to remember? ▶ 51:25

That is a design choice. Episodic memory sidesteps it heuristically: remember everything. Semantic memory needs a separate module that decides what's important, and you can give it demonstrations of what counts as important and the format to store it in.

This is where things get tricky ▶ 52:29. Earlier this year, people were using OpenClaw to manage their email, and for one user it started deleting emails and kept going despite "please stop". The user had said at the start: confirm with me before such actions. The cause was the context-memory compression step: to store memory efficiently, the model kept only what it judged important, and "confirm before you act" wasn't judged important. Memory must be faithful as well as compact. Replay the failure:

A mock compressor gives each event an importance score (scripted numbers) and keeps the top $k$. Shrink the budget and watch what the agent does next.

Going beyond the lecture. Pinning standing instructions outside the compressible context (a system prompt, or a rules file the harness re-injects every turn) is one common fix; another is to make destructive tools require confirmation in code rather than trusting the model to remember to ask.

Key takeaways

  1. Multi-agent debate boosted weak models; with strong models it adds little accuracy, but multi-agent designs still help with efficiency and data access control.
  2. Orchestrators (e.g. Magentic-One) decompose a task and route the parts to specialist agents, then merge the results.
  3. Memory exists because context is finite and relevance is hard. Episodic = raw log, semantic = synthesised facts, procedural = reusable skills (Voyager's skill library).
  4. Deciding what to keep is a design choice with real risk: a compression step that dropped "confirm first" led OpenClaw to keep deleting a user's email.
  5. Tool use began inside decoding (Toolformer, five tools) and scaled to thousands of APIs with retrieval (Gorilla, 1,600+), cutting hallucination by delegating.
