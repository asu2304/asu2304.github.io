Compound AI Systems: Workflows, Agents, Tool Calls and MCP

Real products wrap an LLM in other components: a compound AI system. Think of it in three layers (system, data, evaluation), and at the system layer ask one question first: who decides the next step? In a workflow the script does; in an agent the model does. Underneath both sits the humble tool call, and the Model Context Protocol standardises how tools plug in.

1 · Three layers of a compound AI system ▶ 53:41

How real products combine an LLM with other components is what we call a compound AI system. With an LLM core, planning, memory, environment and more, it's easy to feel overwhelmed; a more principled engineering view helps. The course is organised in the same three layers:

Layer ▶ 54:32What it covers
SystemThe architecture: which components the agent has and how they connect (everything on the previous pages)
DataWhat the agent learns from or is prompted with: training examples (e.g. SWE-smith, later in the course), task demonstrations, or simply the context you give it
EvaluationHow you judge whether the agent works, including the metric itself. The wrong metric can make a weak agent look good, so metrics deserve a lot of care
When an agent isn't working as expected, a good first question is which layer the problem is in: system, data or evaluation? ▶ 55:40

2 · Workflow vs agent: who decides the steps? ▶ 56:02

A key system-layer design choice is who decides the steps (and what to remember, and so on): the agent, or something else? Both answers are compound AI systems (a large model plus other components), and you'll meet both terms:

WorkflowAgent
Who picks the next stepA fixed scriptThe LLM itself
Role of the LLMWorks inside each stage, never picks the next oneSets its own course: what to open, what to run, when it's done
Example (fixing a GitHub issue)Agentless: find the file → write a patch → run tests, always in that orderSWE-agent: chooses which files to open, what to run, and when to stop
Trade-offPredictableMore flexible, and more responsibility on the model

So why have workflows at all? ▶ 57:30 Because they can be very strong. AlphaCode 2 generates up to millions of candidate programs, then tests and ranks them, reaching roughly the level of 87% of human competitors (as said in the lecture), a huge jump over AlphaCode 1.

RAG ▶ 58:00, another workflow widely used in industry, grew out of open-domain question answering. Retrieval-augmented generation connects an LLM to external knowledge stores in real time: for a query that needs, say, a weather website, fetch the relevant content, add it to the query as context, then generate, giving more factual and consistent answers.

Below, the same toy bug fix is run both ways, with a knob for how reliable each single step is.

Going beyond the lecture. This model is mine, and crude: steps fail independently, and an agent that notices a failure fixes it with probability $r$. It shows why both designs survive. Errors compound along a chain (0.95 per step is only $0.95^{20}\approx0.36$ after 20 steps), so a short fixed pipeline is hard to beat when the task fits it; an agent spends more steps but can observe and repair its mistakes, which a fixed script can't. 3 · What happens in a single tool call ▶ 58:44

From a system perspective, one tool call has several stages:

  1. Select a tool from the schemas available in context.
  2. Fill arguments: fill each field from the task.
  3. Validate: check the arguments against the schema. Sometimes constrained decoding enforces it, so the model can't even produce an ill-formed call.
  4. Execute, usually in a sandbox.
  5. Return: the result goes back into the context.

The lecture's example: "What does test.py contain?" → the model calls read_file, fills path, the path is checked to be a string, and the file contents come back for the user. Build calls yourself, including broken ones:

    4 · The Model Context Protocol ▶ 60:00

    If every AI application had to write a custom integration for every tool, nothing would scale. MCP is a standard protocol for that connection. On one side, AI applications: Claude Desktop, IDEs, code editors such as Claude Code. On the other, data sources and tools: databases (SQL), Google Drive, deployment tools, productivity tools such as Slack, Google Maps. MCP sits in the middle, with data flowing both ways. Build a tool once as an MCP server, and any MCP client can set it up and use it. (Next class goes deeper.)

    custom integrations ($N\times M$)
    with MCP: one client per app + one server per tool ($N+M$)
    Going beyond the lecture. Under the hood, MCP messages are JSON-RPC 2.0. A client discovers tools with {"method":"tools/list"}, and the server replies with each tool's name, description and JSON Schema for its inputs; then the client calls one with {"method":"tools/call","params":{"name":"read_file","arguments":{"path":"test.py"}}}. Those schemas are exactly what the model selects from in stage 1 of the tool call above. Servers can also expose resources and prompts, not just tools.

    Key takeaways

    1. A compound AI system is an LLM plus other components. Analyse it in three layers (system, data, evaluation) and debug by asking which layer is at fault; a bad metric can make a weak agent look good.
    2. Workflow vs agent is about who decides the next step: a fixed script (Agentless) or the model (SWE-agent).
    3. Workflows can be very strong: AlphaCode 2's generate-test-rank pipeline and RAG's retrieve-then-generate.
    4. One tool call = select → fill arguments → validate against the schema (maybe constrained decoding) → execute in a sandbox → return the result to context.
    5. MCP turns N×M custom integrations into a standard: build a tool once as a server, use it from any client.
