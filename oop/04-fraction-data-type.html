Your Own Data Type: Fraction

This is OOP's headline promise made concrete: he builds a Fraction data type that you can print and add, subtract, multiply and divide with ordinary operators. The trick is a handful of magic methods: __str__ decides what print shows, and __add__, __sub__, __mul__, __truediv__ decide what + − * / do.

1 · The problem: no fraction type ▶ 1:06:18

Write five-sixths and Python immediately turns it into a decimal:

x = 5/6
print(x)
0.8333333333333334

Python (like most languages) has no built-in data type that keeps fractions as fractions. So we build one: a class that supports addition, subtraction, multiplication and division of fractions, and anything else you would do with fractions in maths.

Going beyond the video: the standard library does ship one, from fractions import Fraction, which also reduces automatically (Fraction(4, 5) * Fraction(5, 6) gives 2/3). Building our own is still the best way to see how such a type works.

2 · Data first: a parameterised constructor ▶ 1:07:03

What data does a fraction object need? A numerator and a denominator. Whoever creates the object should hand over these two numbers, so the constructor takes two inputs besides self and stores them on the object:

class Fraction:
    def __init__(self, x, y):
        self.num = x
        self.den = y

x = Fraction(4, 5)
print(type(x))
L = [1, 2, 3, x]       # usable like any other object
print(len(L))
print(x)
<class '__main__.Fraction'>

<__main__.Fraction object at 0x1026d6ee0>

He saves it as fraction.py and imports it (from fraction import Fraction), so the notebook shows <class 'fraction.Fraction'>. Typing Fraction( in the notebook shows the hint that the constructor wants two numbers. x is now a genuine object of type Fraction, as real as an int or a string: you can put it in a list, pass it around. But printing it shows gibberish ▶ 1:09:15: Python doesn't know what a Fraction should look like, and only the class's author can tell it. All it can say is "a Fraction object, at this memory location".

3 · __str__: what print shows ▶ 1:10:01

Recall the magic methods: not called by the object, triggered automatically in a given situation. The constructor triggers on creation. __str__ triggers whenever you put an object of your class inside print(): Python goes into your class, finds this method, and prints what it returns (it must return a string). First, a silly version:

class Fraction:
    def __init__(self, x, y):
        self.num = x
        self.den = y

    def __str__(self):
        return 'hello'

x = Fraction(4, 5)
y = Fraction(1, 2)
print(x)
print(y)
hello
hello

Every fraction prints "hello", because that is the logic we wrote. The proper version uses string formatting ▶ 1:11:44: return '{}/{}'.format(self.num, self.den), after which print(x) shows 4/5. You decide how your data type looks.

4 · x + y fails, and so does adding two sets ▶ 1:12:26

Guess what happens if you add two fraction objects. Nothing works, because you never told Python how to add two of them. Built-in types have the same limit: the author of set never wrote logic for adding two sets.

5 · __add__: teaching Python what + means ▶ 1:13:31

The third magic method in your life: __add__. As soon as you put + between two objects of your class, Python goes into your code, finds this method and runs it. + is a binary operator, it needs two operands, so the method receives two Fraction objects: the one on the left (x) arrives as self, the one on the right (y) as other. Both have a num and a den.

The school maths ▶ 1:14:42: cross-multiply for the new numerator, multiply the denominators.

a/b + c/d = (a·d + c·b) / (b·d)

    def __add__(self, other):
        temp_num = self.num * other.den + other.num * self.den
        temp_den = self.den * other.den
        return '{}/{}'.format(temp_num, temp_den)

He returns the answer in the same 'num/den' format. And reducing it to lowest terms? "That's your job": write one more method (a simplify step) and call it at the end; he leaves it as an exercise.

6 · Subtract, multiply, divide ▶ 1:17:47

x - y also fails until you add the fourth magic method, __sub__: copy __add__ and flip the plus to a minus. Multiplication (__mul__): numerators times numerators, denominators times denominators. Division (__truediv__): flip the second fraction and multiply. The complete class:

class Fraction:

    # parameterized constructor
    def __init__(self, x, y):
        self.num = x
        self.den = y

    def __str__(self):
        return '{}/{}'.format(self.num, self.den)

    def __add__(self, other):
        temp_num = self.num * other.den + other.num * self.den
        temp_den = self.den * other.den
        return '{}/{}'.format(temp_num, temp_den)

    def __sub__(self, other):
        temp_num = self.num * other.den - other.num * self.den
        temp_den = self.den * other.den
        return '{}/{}'.format(temp_num, temp_den)

    def __mul__(self, other):
        temp_num = self.num * other.num
        temp_den = self.den * other.den
        return '{}/{}'.format(temp_num, temp_den)

    def __truediv__(self, other):
        temp_num = self.num * other.den
        temp_den = self.den * other.num
        return '{}/{}'.format(temp_num, temp_den)

The pattern: an operator between two of your objects is translated into a call of a magic method on the left object, with the right object as the argument: x + y → x.__add__(y) → Fraction.__add__(x, y), so self is x and other is y.

7 · Where to go from here ▶ 1:20:17


All four operations work, and you could keep going: fraction to decimal, decimal to fraction, anything you want. You don't have to do anything clever: find the right magic method and implement it. Building an integer-like type? There are magic methods for % (mod), ** (power), >, <, ==, !=, and beyond arithmetic, for converting to hexadecimal, octal, complex, and for type conversion.


Two student stories ▶ 1:21:21. One student built a coordinate-geometry data type: create point and line objects, then the distance between two points, the distance from a point to a line, whether a point lies on a line, whether three points form an equilateral triangle. Another built a complete matrix class. Both got placed partly on the strength of it: they could say "I built a data type anyone can use"; drop the file into a library and people use its objects just like built-ins.


His closing advice: when you design a type, think logically about which magic methods you need, and with that you can build almost anything. Make your own data type, post it publicly, and show it in interviews; it is quite impressive.


Going beyond the video: his methods return strings, so the result is no longer a Fraction: print(type(x + y)) gives <class 'str'>, and chaining x + y + Fraction(1, 30) fails with TypeError: can only concatenate str (not "Fraction") to str. Return a new Fraction instead, and reduce in the constructor with math.gcd (his "simplify" exercise):

from math import gcd

class Fraction:
    def __init__(self, x, y):
        g = gcd(x, y)
        self.num = x // g
        self.den = y // g

    def __str__(self):
        return '{}/{}'.format(self.num, self.den)

    def __add__(self, other):
        return Fraction(self.num * other.den + other.num * self.den,
                        self.den * other.den)

x = Fraction(4, 5)
y = Fraction(5, 6)
z = x + y + Fraction(1, 30)     # chaining works: x + y is a Fraction now
print(z)
print(Fraction(20, 30))

Key takeaways


    

  1. Python has no fraction literal (5/6 becomes a float), so a Fraction class is a perfect "build your own data type" exercise.
    2. 

  2. A parameterised constructor __init__(self, x, y) receives the data and stores it as self.num, self.den.
    3. 

  3. __str__ runs when the object is printed and must return a string; without it you get <… object at 0x…>.
    4. 

  4. Operators call magic methods on the left operand: x + y → x.__add__(y), with self = x and other = y. Likewise __sub__, __mul__, __truediv__.
    5. 

  5. Without the matching magic method you get TypeError: unsupported operand type(s), even for built-ins like set + set.
    6. 

  6. Designing a type = deciding which magic methods it needs. Your own data types make strong portfolio and interview material.
