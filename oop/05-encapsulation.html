Encapsulation: Hiding Data, Name Mangling, Getters and Setters

If every attribute of your class is open, anyone using it can put garbage inside and break your class's own logic. Encapsulation fixes this in two moves: hide the data (a double underscore in front of the name), then give controlled access through a getter and a setter that check what comes in.

1 · First, a name: instance variables ▶ 1:24:11

He picks up the Atm class from part 2. The variables created inside the constructor, self.pin and self.balance, have a proper name: instance variables. Their value is different for every object, which is exactly right: every customer has their own pin and their own balance.

His Atm runs a text menu with input() from __init__. In the snippets below the methods take the pin and amount as arguments instead, so each snippet runs on its own; the logic is the same.

2 · The problem: everything is open ▶ 1:25:08

Create an object, type sbi. and the editor offers every method (create_pin, deposit, withdraw, check_balance, menu) and also the data: pin and balance. An object can reach everything in its class, methods and data alike. So anyone can do this:

class Atm:
    def __init__(self):
        self.pin = ''          # instance variables:
        self.balance = 0       # one copy per object

    def create_pin(self, pin):
        self.pin = pin
        print('Pin set successfully')

    def deposit(self, pin, amount):
        if pin == self.pin:
            self.balance = self.balance + amount
            print('Deposit successful')
        else:
            print('Invalid pin')

sbi = Atm()
sbi.create_pin('1234')
Pin set successfully
sbi.balance = 'hehehe'         # nothing stops this...
sbi.deposit('1234', 50000)     # ...and now the class's own logic breaks
Traceback (most recent call last):
  ...
TypeError: can only concatenate str (not "int") to str

Nothing is wrong with deposit: it adds the amount to the balance. But someone turned the balance into a string, and str + int crashes. Leaving your data open like this is not good practice: a junior programmer on your team can, by mistake or otherwise, make a change that breaks your existing code.

3 · The fix, step 1: hide the data with __ ▶ 1:27:38

In Java you would put an access modifier like private in front of the data: then it can be used inside the class but not outside. Python has no private keyword. Instead you put a double underscore in front of the name, and rename it everywhere it's used in the class (he asks if anyone knows how to find-and-replace in the editor). Methods can be hidden the same way, e.g. __menu.

class Atm:
    def __init__(self):
        self.__pin = ''
        self.__balance = 0

    def __menu(self):          # methods can be hidden too
        pass

    def create_pin(self, pin):
        self.__pin = pin
        print('Pin set successfully')

    def deposit(self, pin, amount):
        if pin == self.__pin:
            self.__balance = self.__balance + amount
            print('Deposit successful')
        else:
            print('Invalid pin')

    def check_balance(self, pin):
        if pin == self.__pin:
            print(self.__balance)
        else:
            print('Invalid pin')

sbi = Atm()
sbi.create_pin('1234')
Pin set successfully

Now type sbi. again: only the public methods show up (in his full class create_pin, deposit, withdraw, check_balance); pin, balance and menu are gone. Only what you want the other person to see. When you create a class, it's good practice to hide your data members, and you can hide methods too if they're internal.

4 · Behind the scenes: name mangling ▶ 1:31:05

How does the hiding work? When the interpreter sees __pin inside class Atm, it internally renames it to _Atm__pin (underscore, class name, then the name). Look inside the object:

print(sbi.__dict__)
print([name for name in dir(sbi) if not name.endswith('__')])
{'_Atm__pin': '1234', '_Atm__balance': 0}
['_Atm__balance', '_Atm__menu', '_Atm__pin', 'check_balance', 'create_pin', 'deposit']

There is no attribute called __balance any more, so asking for it fails:

print(sbi.__balance)
Traceback (most recent call last):
  ...
AttributeError: 'Atm' object has no attribute '__balance'

5 · Two experiments he runs ▶ 1:32:27

Experiment 1. What if someone writes sbi.__balance = 'hehehe'? Think before reading on: will the next deposit crash?

class Atm:
    def __init__(self):
        self.__pin = ''
        self.__balance = 0

    def create_pin(self, pin):
        self.__pin = pin

    def deposit(self, pin, amount):
        if pin == self.__pin:
            self.__balance = self.__balance + amount
            print('Deposit successful')

    def check_balance(self, pin):
        if pin == self.__pin:
            print(self.__balance)

sbi = Atm()
sbi.create_pin('1234')
sbi.__balance = 'hehehe'      # outside the class: no mangling happens
print(sbi.__dict__)
sbi.deposit('1234', 50000)    # works: the methods use _Atm__balance
sbi.check_balance('1234')
{'_Atm__pin': '1234', '_Atm__balance': 0, '__balance': 'hehehe'}
Deposit successful
50000

No crash. Outside the class there is no renaming, so this line just creates a brand-new attribute called __balance. None of the methods use it (they all use _Atm__balance), so it does no harm to your existing logic.

Experiment 2 ▶ 1:34:38. But if someone knows the mangled name:

sbi._Atm__balance = 'hehehe'  # the real (mangled) name
sbi.deposit('1234', 50000)
Traceback (most recent call last):
  ...
TypeError: can only concatenate str (not "int") to str

The code crashes again. Nothing in Python is truly private. If someone finds out that your class has this variable, they can reach it through _ClassName__variable and mess things up.

6 · Why Python lets you: "made for adults" ▶ 1:35:38

The first time he saw this, he was annoyed: Java gives you real privacy, why doesn't Python? Then he found an answer online that made him smile: Python is a language made for adults. If you work in a company and you've hidden a variable, that's an agreement: "don't use this". A colleague who goes around it deliberately has a different problem. And Python's designers don't hide things completely because someday you might genuinely need to get at them. The philosophy: hide it well enough that nobody reaches it by accident; if someone really goes looking, they'll find it.

Going beyond the video. The phrase usually quoted is "we are all consenting adults here". Python also has a weaker convention: a single leading underscore (_balance) means "internal, please don't touch" but is not renamed at all. Double underscore's real job is avoiding name clashes when a subclass reuses the same attribute name; names with underscores at both ends (__init__) are never mangled.

7 · The fix, step 2: getter and setter ▶ 1:38:26

Hiding alone isn't enough: a programmer using your class might genuinely need to see or change the pin. So for each data member you can write two methods: a getter to read it and a setter to change it.

class Atm:
    def __init__(self):
        self.__pin = ''
        self.__balance = 0

    def get_pin(self):
        return self.__pin

    def set_pin(self, new_pin):
        if type(new_pin) == str:
            self.__pin = new_pin
            print('Pin changed')
        else:
            print('Not allowed')

sbi = Atm()
sbi.set_pin('1234')
print(sbi.get_pin())
Pin changed
1234

His question ▶ 1:41:48: first we hid the data, then we gave a setter that changes it anyway. With set_pin the other programmer can do exactly what sbi.pin = … did. So what was the point?

The point is that the change now goes through your code, so you can control it with your own logic. Say your rule is that a pin must always be a string:

sbi.set_pin(5.6)      # breaks our rule: pin must be a string
print(sbi.get_pin())
Not allowed
1234

"You want to see it? Use my function. You want to set it? Go through my logic." The data stays usable and protected.

8 · So what is encapsulation? ▶ 1:44:08

Encapsulation = hide each data member (make it private with __), then bundle it with a getter and a setter so it can still be read and updated, but only through your rules.

Think of a medicine capsule: several powders packed together inside one shell. Here you pack a data member together with its two methods. The need for it: you can't leave data directly open, or someone's edit can break your existing code.

Key takeaways


    

  1. Instance variables (made in __init__ via self) hold a different value for every object.
    2. 

  2. Open data lets anyone break your class's logic (sbi.balance = 'hehehe' then deposit crashes); hide it with a leading __, for data and for internal methods.
    3. 

  3. Python mangles __x inside class C to _C__x. Assigning obj.__x outside just makes a new, harmless attribute; obj._C__x reaches the real one. Nothing is truly private: Python is "made for adults".
    4. 

  4. Getters and setters give access on your terms: the setter validates (e.g. pin must be a str) before storing.
    5. 

  5. Encapsulation = private data + its getter/setter in one capsule. In a class diagram, − marks private and + public.

Going beyond the video. Idiomatic Python often replaces get_x()/set_x() with @property, so the validation runs on plain-looking attribute access:

class Account:
    def __init__(self):
        self.__balance = 0

    @property
    def balance(self):
        return self.__balance

    @balance.setter
    def balance(self, value):
        if type(value) in (int, float) and value >= 0:
            self.__balance = value
        else:
            print('Not allowed')

a = Account()
a.balance = 500       # looks like plain assignment, runs the setter
a.balance = 'hehehe'
print(a.balance)


Not allowed
500
