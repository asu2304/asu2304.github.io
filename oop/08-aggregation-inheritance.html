Class Relationships: Aggregation and Inheritance

Real programs are many classes working together, and two relationships cover most of it. Aggregation is has-a: a Customer has an Address and hands all address work to it. Inheritance is is-a: a Student is a User, so it gets the User's methods, data and constructor without rewriting them.

1 · From one class to many ▶ 2:31:05

Every program so far had a single class doing all the work: Atm in the ATM project, Fraction in the fraction one. A real application is different. Build an e-commerce site and you immediately have Product, Customer, Address, Review and many more, and those classes relate to one another.

There are a few kinds of class relationship, but two major ones show up everywhere:

Quick test: say the sentence out loud. If "X is a Y" sounds right, it's inheritance; everything a Product can do, a SmartPhone can do too. If "X has a Y" sounds right, it's aggregation; one object holds another.

2 · Aggregation: a Customer has an Address ▶ 2:33:44

The class diagram has two boxes. Customer holds a name, a gender and an address, plus methods such as edit_profile. Address holds city, pincode and state. The line between them gets a diamond on the Customer's side, the side of the class that owns the other. Whenever you see that diamond, read "Customer has an Address".

In code, aggregation is nothing more exotic than passing one object into another object's constructor, exactly as you would pass a string or a number. Build the Address first, then hand the whole object to the Customer:

class Customer:

    def __init__(self, name, gender, address):
        self.name = name
        self.gender = gender
        self.address = address

    def edit_profile(self, new_name, new_city, new_pin, new_state):
        self.name = new_name
        self.address.change_address(new_city, new_pin, new_state)

class Address:

    def __init__(self, city, pincode, state):
        self.city = city
        self.pincode = pincode
        self.state = state

    def change_address(self, new_city, new_pin, new_state):
        self.city = new_city
        self.pincode = new_pin
        self.state = new_state

add = Address('Kolkata', 700156, 'WB')
cust = Customer('Nitish', 'Male', add)

print(cust.address.city)
print(cust.address.pincode)

cust.edit_profile('Ankit', 'Gurgaon', 122011, 'Haryana')
print(cust.name, cust.address.city, cust.address.pincode, cust.address.state)

Two things he points out while running it:

  • print(cust.address) on its own prints the whole Address object (something like <__main__.Address object at 0x…>), because cust.address is an object. To get the city you chain one more dot: cust.address.city.
  • Read cust.address.pincode left to right: the customer object → its address attribute (an Address object) → that object's pincode.

3 · The point of aggregation: delegation ▶ 2:40:01

Now add an Edit profile feature. The customer may change their name and move house: a new city, pincode and state (he drops gender from the edit to keep it short). The name belongs to Customer, so Customer sets it. The address belongs to Address, so Customer doesn't touch city or pincode itself. It calls Address's method:

def edit_profile(self, new_name, new_city, new_pin, new_state):
    self.name = new_name
    self.address.change_address(new_city, new_pin, new_state)

That's the last line of the output above: after cust.edit_profile('Ankit', 'Gurgaon', 122011, 'Haryana') the name is Ankit and the address is in Gurgaon. In his words, the Customer class isn't doing the work itself; it's getting the Address class to do it. Anything address-related, now or later (say, adding a second address), goes through Address's methods. That relationship is aggregation.

Going beyond the video: UML separates a hollow diamond (aggregation: the part can live on its own, like an Address that exists before any Customer) from a filled diamond (composition: the part is created and destroyed with its owner). Also remember page 6: cust.address is a reference. If two customers are given the same Address object, one change_address moves both of them.

4 · Inheritance: the idea ▶ 2:43:27

Inheritance is a real-world concept before it's a programming one. Socially and legally, your father's property passes to you. Biologically, many of your facial features come from your parents, because genes carry information from one generation down to the next. OOP was designed to model real-world problems, so it borrowed this idea, and inheritance became one of its most important concepts.

What's the benefit? A Udemy-style site ▶ 2:45:00

Suppose you're building a course website like Udemy. It has two kinds of user: a Student who takes courses and an Instructor who creates them. List what each can do:

Student can…Instructor can…
login, register, enroll in a course, review a course, …login, register, create a course, answer questions, …

A first plan: one class for each, with all of its data and methods. But login and register are the same in both: a student and an instructor log in to the same database in the same way. Writing them twice breaks a basic rule of good code, DRY: Don't Repeat Yourself ▶ 2:47:23.

With inheritance you plan it differently. Make a third class, User, holding only login and register, and let Student and Instructor both inherit from it. Each keeps only its own specific methods; when a student logs in, it uses User's login.

Interview question: what's the biggest benefit of inheritance? Code reusability. On a small example it may look like a minor win, but on a real, large application it saves a lot of time and keeps the code concise and optimised. In his words, you end up thanking yourself for having used it.

5 · The rules of inheritance ▶ 2:49:25

It only flows upward. Student can use User's login and register, but User can't use Student's enroll. Same as the analogy: your father's money is yours, but the money you earn isn't your father's; it goes to your children. (He jokes: don't say this to your father with too much confidence.)

What does a child class inherit? ▶ 2:50:11 When a child class inherits a parent class, it gets three things:

  1. all the data members (attributes),
  2. all the member functions (methods),
  3. the constructor.

And one exception to always remember: private members are not inherited. Anything with a double underscore in the parent can't be reached from the child (section 9).

6 · Inheritance in code ▶ 2:51:32

A stripped-down version of the Udemy example. There's no real logic inside the methods (we aren't building the app, just watching inheritance work), so each one prints its name. The only new syntax is the parent's name in brackets after the child's: class Student(User): tells Python that Student is a subclass of User, so User is the parent and Student the child.

class User:

    def login(self):
        print('login')

    def register(self):
        print('register')

class Student(User):

    def enroll(self):
        print('enroll')

    def review(self):
        print('review')

stu1 = Student()
stu1.enroll()
stu1.review()
stu1.login()
stu1.register()

u = User()
u.enroll()

AttributeError: 'User' object has no attribute 'enroll'

The student object called all four methods: two of its own, two from its parent. The last line shows the reverse is impossible: the User class has no method called enroll, so a User object can't call it. Two lessons: how to make a class inherit, and that a parent can't reach the child's members.

8 · The constructor is inherited too ▶ 2:57:07

New example, which carries on into the next page: a Phone class and a SmartPhone class that inherits from it. SmartPhone has no constructor of its own; Phone has one that takes price, brand and camera.

class Phone:
    def __init__(self, price, brand, camera):
        print("Inside phone constructor")
        self.price = price
        self.brand = brand
        self.camera = camera

class SmartPhone(Phone):
    pass

s = SmartPhone(20000, "Apple", 13)
print(s.brand)
Inside phone constructor
Apple

What Python does on SmartPhone(20000, "Apple", 13): it goes into SmartPhone looking for a constructor. There isn't one. It notices that SmartPhone inherits from Phone, goes there, finds Phone's constructor and gives it the three values. So "Inside phone constructor" prints and s.brand is Apple.

Rule: if class B inherits class A and B has no constructor, creating a B object calls A's constructor.

9 · Private members are not inherited ▶ 2:59:43

Same code, one change: make brand private with a double underscore. Can the child-class object still reach it? By the rule above it shouldn't, since a child object can access only the parent's public attributes:

class Phone:
    def __init__(self, price, brand, camera):
        print("Inside phone constructor")
        self.price = price
        self.__brand = brand
        self.camera = camera

class SmartPhone(Phone):
    pass

s = SmartPhone(20000, "Apple", 13)
print(s.__brand)
Inside phone constructor
Traceback (most recent call last):
  ...
AttributeError: 'SmartPhone' object has no attribute '__brand'

The constructor still ran (it was inherited), but the private attribute isn't reachable from the child object. A child class's object can't access the parent's private members.

Going beyond the video: "not inherited" really means "hidden by name mangling" (page 5). The value is stored on the object, as _Phone__brand, so s._Phone__brand gives Apple. A trap that catches people: inside a SmartPhone method, self.__brand is mangled to self._SmartPhone__brand, which doesn't exist. Use a public getter on the parent instead, as page 9's examples do.

    Key takeaways

    1. Big programs have many classes; the two major relationships between them are aggregation (has-a) and inheritance (is-a).
    2. Aggregation means one object holding another (Customer(…, address)) and delegating to it (self.address.change_address(…)). Diagram: diamond at the owner.
    3. Inheritance (class Student(User):) exists for code reuse (DRY). It flows upward only: a child can use the parent's members, never the reverse. Diagram: triangle at the parent.
    4. A child inherits the parent's data members, methods and constructor. If the child has no __init__, the parent's runs.
    5. Private (__x) members of the parent can't be accessed through the child.
