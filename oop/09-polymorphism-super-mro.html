Method Overriding, super() and the MRO

When a child and its parent both define the same method, the child's version wins; that's method overriding, the first kind of polymorphism. super() lets the child call the parent's method or constructor anyway, so common work stays in the parent. With multiple parents, the method resolution order (MRO) decides whose method runs.

1 · Method overriding ▶ 3:01:00

Back to Phone and SmartPhone. SmartPhone still has no constructor, but now both classes have a method with the same name, buy. Creating the object runs Phone's constructor as before. Then s.buy(): whose buy runs?

class Phone:
    def __init__(self, price, brand, camera):
        print("Inside phone constructor")
        self.__price = price
        self.brand = brand
        self.camera = camera

    def buy(self):
        print("Buying a phone")

class SmartPhone(Phone):
    def buy(self):
        print("Buying a smartphone")

s = SmartPhone(20000, "Apple", 13)
s.buy()
Inside phone constructor
Buying a smartphone

SmartPhone's. Python starts looking in the object's own class, finds buy there and stops. This is method overriding: if the parent and the child both have a method with the same name, a child object calling it always runs its own class's version.

The real-world version ▶ 3:03:15. Your grandfather started a family business, your father runs it, your elder brother has joined it. You've decided to be a software developer. You had the option of the family business (the inherited method), but where the two conflict you follow your own choice. Same rule: if my parent has something and I have the same thing, I use mine.

Method overriding belongs to polymorphism ▶ 3:02:42, which comes in three kinds: method overriding (here), method overloading and operator overloading (both on page 10).

Puzzle 1. Child has no constructor, Parent has one that stores a private number:

class Parent:

class Child(Parent):

Child has no __init__, so Parent's runs and stores 100 in the private __num. get_num is Parent's method, so it can read Parent's private attribute and returns 100. Simple.

Puzzle 2 ▶ 3:05:58. This time both classes have a constructor:

class Parent:

    def __init__(self, num):
        self.__num = num

    def get_num(self):
        return self.__num

class Child(Parent):

    def __init__(self, val, num):
        self.__val = val

    def get_val(self):
        return self.__val

son = Child(100, 10)
print("Parent: Num:", son.get_num())
print("Child: Val:", son.get_val())
Traceback (most recent call last):
  ...
AttributeError: 'Child' object has no attribute '_Parent__num'

Why? Child(100, 10) runs the Child's constructor, which only sets __val. Parent's constructor never runs, so the line that would create __num never executes. When get_num later looks for it, it simply doesn't exist (the error shows its mangled name, _Parent__num).

Rule: if the child has no constructor, the parent's constructor is called automatically. If the child has its own constructor, the parent's is not called. (Section 4 shows how to call it yourself.)

Puzzle 3 ▶ 3:09:02. A trick question about which var1 gets printed:

class A:
    def __init__(self):
        self.var1 = 100

    def display1(self, var1):
        print("class A :", self.var1)

class B(A):
    def display2(self, var1):
        print("class B :", self.var1)

obj = B()
obj.display1(200)
class A : 100

The 200 goes into the parameter var1, but the method prints self.var1, the attribute the inherited constructor set to 100. Read carefully: a parameter and an attribute with the same name are different variables.

3 · super(): calling the parent's version ▶ 3:10:20

Overriding hides the parent's method. But what if the child wants to add to it rather than replace it? Use the super keyword: from inside a child class, super() lets you invoke the parent's methods and the parent's constructor.

class Phone:
    def __init__(self, price, brand, camera):
        print("Inside phone constructor")
        self.__price = price
        self.brand = brand
        self.camera = camera

    def buy(self):
        print("Buying a phone")

class SmartPhone(Phone):
    def buy(self):
        print("Buying a smartphone")
        super().buy()

s = SmartPhone(20000, "Apple", 13)
s.buy()
Inside phone constructor
Buying a smartphone
Buying a phone

Trace it. Creating the object runs Phone's constructor. s.buy() goes to SmartPhone's buy (overriding), which prints its line. Then super().buy() sends control up to Phone's buy, which prints its line, and control returns to the child.

super() only works inside the class ▶ 3:12:08. You can't write s.super().buy() from outside:

class Phone:
    def __init__(self, price, brand, camera):
        print("Inside phone constructor")
        self.brand = brand

    def buy(self):
        print("Buying a phone")

class SmartPhone(Phone):
    def buy(self):
        print("Buying a smartphone")

s = SmartPhone(20000, "Apple", 13)
s.super().buy()
Inside phone constructor
Traceback (most recent call last):
  ...
AttributeError: 'SmartPhone' object has no attribute 'super'

If you ever see super used outside a class in a problem, that's the bug. He also notes that super can reach the parent's methods and constructor but not its attributes:

class Phone:
    def __init__(self, price, brand, camera):
        self.brand = brand

class SmartPhone(Phone):
    def show(self):
        print(super().brand)

s = SmartPhone(20000, "Apple", 13)
s.show()
Traceback (most recent call last):
  ...
AttributeError: 'super' object has no attribute 'brand'

To read the parent's data, use self.brand: the attribute was stored on the object itself (section 5).

Going beyond the video: the precise rule is that super() looks things up on the classes further along the MRO, never on the object. Instance attributes such as brand live on the object, so super can't see them; a class attribute defined in the parent (for example kind = "phone") is reachable as super().kind.

4 · super() in the constructor ▶ 3:12:54

This is where super really earns its place. Now SmartPhone has its own constructor, which takes five values: price, brand and camera, plus os and ram. Price, brand and camera belong to every phone, so they're Phone's attributes; os and ram are smartphone-specific. So the child says: the common things I'll hand to my parent's constructor, the uncommon ones I'll handle myself.

class Phone:
    def __init__(self, price, brand, camera):
        print("Inside phone constructor")
        self.__price = price
        self.brand = brand
        self.camera = camera

class SmartPhone(Phone):
    def __init__(self, price, brand, camera, os, ram):
        print("Inside smartphone constructor")
        super().__init__(price, brand, camera)
        self.os = os
        self.ram = ram

s = SmartPhone(20000, "Samsung", 12, "Android", 2)
print(s.os)
print(s.brand)
Inside smartphone constructor
Inside phone constructor
Android
Samsung

Control flow: the child's constructor starts (first line printed) → super().__init__(…) jumps up into Phone's constructor, which prints and sets price, brand and camera → control comes back down and sets os and ram. Both s.os and s.brand work. You'll see this pattern constantly in real code: the child does only the child-specific work and delegates everything already written to the parent via super(). He calls it the most important use of super.

Going beyond the video: he advises putting the super().__init__(…) call first in the child's constructor. That's a good habit (the parent's setup runs before the child builds on it), but unlike Java, Python doesn't enforce it: the call can go anywhere in __init__, and any attribute the parent sets will overwrite one the child set earlier.

Can the child use self to reach the parent's attribute? ▶ 3:17:42 Up to now we read parent attributes from outside, via the object. Here a child method reads self.num, which the parent's constructor set:


class Parent:
    def __init__(self):
        self.num = 100

    def __init__(self):
        super().__init__()

The answer hides in knowing what self is (page 3). Calling son.show() passes son in as self. If the son object can access a parent attribute from outside, then self, which is that object, can do the same from inside. Know who self is and you won't get this kind of question wrong.


Parent object vs child object ▶ 3:19:58:

Child: 200


dad is a Parent, so it uses Parent's show. son's constructor first calls the parent's (setting num to 100), then sets var to 200; son.show() runs the child's show because of overriding.

The conflict ▶ 3:29:30. Now both parents have a buy method. Which one does a SmartPhone run?


class Phone:
    def __init__(self, price, brand, camera):
        print("Inside phone constructor")
        self.brand = brand

    def buy(self):
        print("Buying a phone")

class Product:
    def buy(self):
        print("Product buy method")

class SmartPhone(Product, Phone):
    pass

s = SmartPhone(20000, "Apple", 12)
s.buy()
print(SmartPhone.mro())


Inside phone constructor
Product buy method
[<class '__main__.SmartPhone'>, <class '__main__.Product'>, <class '__main__.Phone'>, <class 'object'>]


Product's, because Product is written first in class SmartPhone(Product, Phone). Swap the order to (Phone, Product) and the answer flips:


Inside phone constructor
Buying a phone
[<class '__main__.SmartPhone'>, <class '__main__.Phone'>, <class '__main__.Product'>, <class 'object'>]


(The constructor still comes from Phone in both cases: Product has no __init__, so the search moves on.) The order in which you inherit decides priority, and this concept is called the MRO, method resolution order ▶ 3:30:41. Nothing to fear: the class you inherit from first wins. SmartPhone.mro() (the last line of each output) shows the full search order.


Going beyond the video: "first-listed parent wins" is exactly right for the flat case above. For deeper hierarchies Python uses the C3 linearisation: L[C] = C + merge(L[B1], …, L[Bn], [B1, …, Bn]). Repeatedly take the first head that doesn't appear in the tail of any list. That keeps two promises: a class always comes before its parents, and parents keep the order you listed them in. In a diamond (B and C both inherit A, D inherits both), A comes after both B and C. If no order can keep both promises, Python refuses to create the class.

    8 · Two tricky questions ▶ 3:31:02
    

    Question 1. Three classes in a multilevel chain, with overriding at each level. Answer quickly:
    

    class A:
    def m1(self):
        return 20

class B(A):
    def m1(self):
        return 30

    def m2(self):
        return 40

class C(B):
    def m2(self):
        return 20

obj1 = A()
obj2 = B()
obj3 = C()
print(obj1.m1() + obj3.m1() + obj3.m2())
    

    70
    

    obj1.m1() is A's own: 20. obj3.m1(): C has no m1, so look at the parent before the grandparent. B has one: 30. (If you don't have it but both your father and your grandfather do, your father's is used.) obj3.m2(): C's own, 20. Total 70.
    

    Question 2 ▶ 3:33:15. Every class has m1, and the child methods build on each other:
    

    class A:
    def m1(self):
        return 20

class B(A):
    def m1(self):
        val = super().m1() + 30
        return val

class C(B):
    def m1(self):
        val = self.m1() + 20
        return val

obj = C()
print(obj.m1())
    

    Traceback (most recent call last):
  ...
RecursionError: maximum recursion depth exceeded
    

    obj.m1() runs C's m1 (overriding). C's m1 calls self.m1(), and self is the C object, so that calls C's m1 again, which calls it again… There's no stopping condition, so you get infinite recursion and Python gives up with "maximum recursion depth exceeded". (Had C written super().m1(), it would have been 20 + 30 + 20 = 70.) Once more, the key is knowing who self is: the same object you'd use outside the class.
