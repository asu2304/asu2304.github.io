Mixture of Experts

Replace the one big MLP in each transformer layer with many smaller MLPs, the experts, and let a small router send each token to only a few of them. The model gets the parameters (memory) of all experts but pays the compute of only the active ones: that is what “30B-A3B” means.

1 · The other half of the transformer: the MLP ▶ 32:44

A transformer alternates attention with an MLP (multi-layer perceptron, i.e. a fully connected network; "MLP" and "FFN" are used interchangeably). The MLP is applied independently at each position. So far everything was about attention; now the MLP.

The obvious way to scale the MLP is to make it wider, but that raises compute and memory together. With a $d\times d$ matrix, doubling $d$ makes the matrix–vector product cost 4× as much. People found a more parallel way to scale.

2 · Many experts, few active ▶ 34:12

Dense MLP
input vector $v$ → one big $d\times d$ network → output $o$.
Mixture of experts
input $v$ → router picks a few of experts $E_1,\dots,E_m$ (each an MLP) → weighted average of their outputs.

The other experts exist, sitting in memory, but are not used for this input. Different tokens choose different experts.

This disentangles memory from compute. Memory, i.e. the parameter count, is large because there are many experts. Compute is small because only a few are active per token: for example 8 active out of 128 in total. You can have a trillion-parameter model whose per-token computation is far smaller.

3 · Reading “30B-A3B” ▶ 36:18

That is why large open models are no longer described by one number like "7B". Instead you see names like 30B-A3B:

  • 30B: total parameters, counting every expert.
  • A3B: active 3B. When the model processes a token, only 3B parameters are used in the computation. The rest may be used for other tokens or positions, but not this one.

An illustrative parameter count: shared parts (attention, embeddings) are always active; of the expert MLPs, only $k$ routed ones (plus any shared experts) run per token.

4 · Do the experts specialise? ▶ 37:22

The original motivation, apart from systems, was specialisation: expert 1 for maths, expert 2 for physics, expert 3 for everyday English, expert 4 for code, and so on. Each token would run the relevant specialists, and specialised networks can be smaller for the same performance.

Nobody trains them to specialise explicitly. They may become specialised naturally, because that is an efficient way to reduce the loss: if all were general-purpose, that probably wouldn't minimise the loss best. Some papers report strong specialisation, though it depends on how you define and interpret it.

Experts are chosen per token and per layer, not per sequence. Each layer has an MLP at every position $1,\dots,T$, and at each one the router decides again.

So it's unclear how much specialisation is really possible. Even a sequence that is all maths does not run the same "maths experts" everywhere. Empirically the number of distinct experts a sequence uses is smaller than the total, but the effect is not sharp.

Could you train each expert separately on its own domain? Some people have tried; it doesn't seem to work as well as end-to-end training. It is also cumbersome: you need enough data for each domain (you may have plenty of maths, not of everything). With 8 experts and one chosen at a time, training them separately sounds at least plausible, though the lecturer knows of no public paper doing it well. With 256 experts and 8 chosen, deciding the roles of 256 experts a priori is much harder.

5 · The router ▶ 41:37

How is the choice made? By a relatively small routing module, itself learned. Design choices vary; here is one. The input is $h$, the hidden vector at this position (the $v$ above).

  1. Score every expert. Project with a routing matrix $W_r$ to an $m$-dimensional vector, $m$ = total number of experts, and squash: $$r=\sigma(h\,W_r)\in\mathbb R^m ,$$ with $\sigma$ a softmax or sigmoid. $r$ holds the relative importance of the $m$ experts.
  2. Keep the top $k$. $S$ = the indices of the $k$ largest entries of $r$; $|S|=k$ is the number of active experts (e.g. $k=8$, $m=128$).
  3. Run only those experts: compute $E_s(h)$ for each $s\in S$.
  4. Mix with renormalised weights. $$\operatorname{out}=\sum_{s\in S}\alpha_s\,E_s(h),\qquad \alpha_s=\frac{r_s}{\sum_{s'\in S} r_{s'}} .$$ The $\alpha_s$ sum to 1 over the chosen set, so the output is a convex combination and its scale doesn't change much.

6 · Shared experts ▶ 46:08

Sometimes some of the $m$ experts are shared: always used, at every position and every layer, while the rest are routed as above. DeepSeek-V3 does this. The rationale in that paper is that a shared expert holds common knowledge, say of the English language, that every token needs, and the routed experts specialise. Other models don't use shared experts.

7 · Keeping the load balanced ▶ 47:09

Training MoE models is subtle, and the lecturer skips most of it. One key ingredient: regularisation that pushes the routing to be as uniform as possible. Two reasons:

  1. Wasted parameters. If the router always picks the same two experts, the others are stored for nothing. The effective model is smaller than its parameter count, which is inefficient.
  2. Infrastructure. Experts live on different GPU cards. If usage is very uneven, some cards sit idle while others are overloaded, and inference efficiency drops.

There are other remedies, such as giving popular experts more GPUs. A DeepSeek paper even describes changing the number of GPUs per expert dynamically: during US daytime some experts are used more, and during China's daytime others are, probably because languages and use cases shift. (The lecturer isn't sure all models do this.)

A toy router with $m=16$ experts, random fixed $W_r$ and a sigmoid. “Router bias” tilts the scores towards low-numbered experts, mimicking a router that has collapsed onto a few favourites (what load-balancing regularisation prevents).

Going beyond the lecture. A common form of the balancing regulariser (from the Switch Transformer) adds $\lambda\, m\sum_s f_s P_s$ to the loss, where $f_s$ is the fraction of tokens routed to expert $s$ and $P_s$ the average router probability for $s$; it is smallest when both are uniform. DeepSeek-V3 instead adjusts a per-expert bias on the router scores up or down during training, which is the reverse of the "router bias" slider here.

8 · Why bother: parameters without the compute ▶ 49:19

Asked whether MoE is only about GPU efficiency, the lecturer says that in the end it largely is about efficiency. A 30B-A3B model has 30B parameters but each token costs only about 3B parameters of compute. The other parameters only need to sit in memory, they aren't computed with; if you are compute-bound at test time, that is a real benefit.

Compare a dense model with 1 trillion parameters, literally. There is almost no chance to serve it: the latency would be far too long, serving would cost too much, and the price on the website would be so high that nobody would use it. A non-MoE trillion-parameter model is almost impossible. A trillion-parameter MoE with maybe 30B active costs about as much as a 30B model while keeping the benefit of many more parameters.

Key takeaways

  1. MoE replaces a layer's MLP with $m$ expert MLPs; a router sends each token to $k$ of them and averages their outputs.
  2. Total parameters (memory) and active parameters (compute) come apart: “30B-A3B” = 30B total, 3B active per token.
  3. Routing is per token and per layer. Specialisation may emerge but is not trained explicitly and is not sharp.
  4. Router: $r=\sigma(hW_r)$, keep the top-$k$ indices $S$, output $\sum_{s\in S}\alpha_sE_s(h)$ with $\alpha_s=r_s/\sum_{s'\in S}r_{s'}$. Some models add always-on shared experts.
  5. Training regularises the routing towards uniform use, so no parameters are wasted and GPUs stay evenly loaded.
